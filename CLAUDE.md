# Turtle Trips (tt) — app self-hosted de gestión de viajes

Multi-usuario con login propio (cookie de sesión). Vue 3 + FastAPI + SQLite, una sola imagen Docker donde FastAPI sirve la SPA compilada desde `backend/static/`. UI multi-idioma (es/en) con vue-i18n; los comentarios del código siguen en español.

## Comandos

```bash
./dev.sh             # dev con hot reload — trabaja SIEMPRE en http://localhost:5173
                     # (`back`/`front` para solo uno; `--open` abre el navegador)
                     # en dev :8000 solo sirve la API (TT_SERVE_STATIC=0): nada de builds

# Backend (desde backend/, dependencias gestionadas con uv + uv.lock)
uv run pytest                                      # tests
TT_DATA_DIR=../data uv run uvicorn app.asgi:app --reload
TT_DATA_DIR=../data uv run alembic upgrade head
uv run alembic revision --autogenerate -m "…"      # tras cambiar models.py

# Frontend (desde frontend/)
npm run dev          # dev server :5173 con proxy /api → :8000
npm run build        # → dist/ (incluye sw.js + manifest de la PWA)
npm run typecheck    # vue-tsc
npm test             # vitest (lógica pura: utils/ y composables/)

# Todo junto
docker compose up --build
```

## Arquitectura

- `backend/app/models.py` — todas las entidades SQLAlchemy. Trip → places/itinerary/bookings/expenses/attachments/packing_items con cascade delete. `Trip.status` es una property derivada de fechas salvo `status_override`. `Trip.countries` es JSON con códigos ISO alpha-2; `cover_image` es la portada subida (endpoints `/trips/{id}/cover`).
- **Auth** (`app/auth.py` + `routers/auth.py`): sesiones server-side — token `secrets.token_urlsafe` guardado como sha256 en tabla `sessions`, cookie `tt_session` HttpOnly SameSite=Lax con caducidad sliding (TT_SESSION_TTL_DAYS, TT_COOKIE_SECURE); passwords con bcrypt (TT_BCRYPT_ROUNDS, los tests lo bajan a 4). CERO claves de firma que gestionar. `User` (username unique case-insensitive, is_admin, theme light|dark|system, language es|en) va 1:1 con su `Traveler` (`traveler_id` UNIQUE RESTRICT); los viajeros sin cuenta son "virtuales". Bootstrap: con 0 usuarios, `POST /auth/bootstrap` crea el admin (reutiliza familia y viajero por nombre si existen); después solo el admin crea cuentas (`routers/admin.py`: CRUD /users con `traveler_id` XOR `traveler_name`, reset de password que revoca sesiones, guarda del último admin). En `main.py` los routers se registran en 3 bloques: protegidos (`Depends(get_current_user)`), admin (`require_admin`: /users y /backup) y públicos (auth + `itinerary.public_router` con el feed .ics). `GET /auth/me` devuelve user+traveler+family; `PATCH /auth/me/settings` persiste tema/idioma; `POST /auth/me/password` revoca las demás sesiones.
- **Recuperación de contraseña** (tabla `password_reset_tokens`, endpoints públicos `POST /auth/forgot-password` y `GET`/`POST /auth/reset-password`): sin correo saliente, el enlace se ESCRIBE EN LOS LOGS del servidor (banner enmarcado por el logger `tt.auth`, que `main._configure_logging` engancha a stderr con el formato de uvicorn) y lo reparte el admin desde `docker logs`. El token va como el de sesión (sha256 en DB), es de UN SOLO USO, caduca con `TT_PASSWORD_RESET_TTL_MINUTES` (60) y pedir otro invalida el anterior; forgot responde 204 exista o no la cuenta (no filtra usuarios) y el GET valida el enlace ANTES de pedir la contraseña (caducado = mensaje, no un formulario que falla). La URL sale del `Origin` de la petición (detrás del reverse proxy `base_url` solo conoce el puerto interno). Al confirmar: revoca TODAS las sesiones del usuario y deja la nueva abierta (auto-login) → el front redirige a la lista de viajes. Front: rutas `/forgot-password` y `/reset-password?token=` (public+bare), `components/auth/AuthCard.vue` es el marco común de las tres pantallas de acceso (tortuga + título + selector de idioma), `extractResetToken` (utils/auth) traga la URL entera o el token pelado — quien no llegue por el enlace puede pegarlo — y `AUTH_ROUTES` (router) marca dónde está la frontera del splash para App.vue.
- **Familias** (`Family`, `routers/families.py`): agrupan VIAJEROS (con o sin cuenta) vía `Traveler.family_id` (nullable, cambiarlo es solo-admin); el usuario hereda la familia de su viajero. Scoping por familia: mapa mundial, categorías y plantillas de maleta (`family_id` NOT NULL + uniques por familia); `Trip.family_id` = familia del creador (define qué categorías/plantillas usa el viaje). `GET /families` es legible por cualquier usuario (nombres en badges); mutaciones solo admin; crear familia siembra sus categorías default; borrar exige familia vacía (sin viajeros ni viajes). Orden manual con `Family.position` (`POST /families/reorder` con ids en orden, solo admin; el listado ordena por position). Alta de viajero: `TravelerCreate.family_id` opcional (ausente = familia del creador; un no-admin solo puede elegir la suya o ninguna).
- **Scoping de viajes** (`routers/common.py`): acceso = tu viajero está en `trip.travelers` (`ensure_trip_member`, 403; el ADMIN tiene bypass total y ve todos los viajes); mutaciones planas via `get_trip_scoped`/`delete_trip_scoped` (resuelven `obj.trip_id`). `require_family` (403 accionable) para crear viajes y recursos de familia. Al crear un viaje el creador no-admin queda SIEMPRE como viajero; guarda 409 si quitar viajeros dejaría el viaje sin nadie con cuenta (huérfano). Todos los miembros pueden editar TODO (incluido borrar) — única excepción: las maletas (matriz por familia, ver **Maleta**).
- **Viajeros** (`Traveler`) son un pool GLOBAL (viajes conjuntos entre familias) y se asocian a viajes vía tabla `trip_travelers` (M2M). Tienen `avatar_image` (endpoints `/travelers/{id}/avatar`, ficheros en `uploads/avatars/`) y property `has_user`. Permisos de edición: el propio viajero o cualquier virtual; el de OTRO usuario solo admin; DELETE 409 si tiene cuenta. `Expense.paid_by_id` apunta a travelers. La asociación se edita desde el formulario de crear/editar viaje (`TripFormDialog`, campo "Viajeros" con creación inline y el propio viajero preseleccionado al crear): `TripCreate`/`TripUpdate` aceptan `traveler_ids` (en update REEMPLAZA el conjunto; ausente = no lo toca) además de los endpoints planos `POST/DELETE /trips/{id}/travelers/{traveler_id}`.
- **Reparto de gastos** (Splitwise-like): `Expense.split_mode` (equal|amount|percent) + tabla `expense_shares` (`value` NULL en equal). Sin filas = reparto implícito a partes iguales entre los viajeros ACTUALES del viaje (sin backfill). Cálculo en `services/balances.py` (mayor resto a céntimos sobre `amount_base`, liquidación greedy) expuesto en `GET /trips/{id}/balances`; UI en la vista "Saldos" de la pestaña Gastos (`BalancesPanel.vue` + `ExpenseSplitEditor.vue` en el form; lógica espejo en `composables/useSplit.ts`). El CSV no importa/exporta repartos (quedan "entre todos").
- **Fondo común**: `Expense.paid_by_common` marca gastos pagados del monedero común (pagador virtual, NO un Traveler). Excluyente con `paid_by_id` (el router lo garantiza: marcar uno desmarca el otro). Cuentan en totales/summary pero NO en balances (contadores `common_*` en TripBalances). En la UI es la opción "Fondo común" (cartera ámbar) del selector de pagador ÚNICO (`PayerSelect.vue`: construye sus opciones desde `travelers` — con avatar — y los centinelas que pida el contexto vía `lead` 'unassigned'|'all'|null e `includeNone`; lo usan el form de gasto, el de reserva, los filtros y la edición en bloque; `PayerTag.vue` pinta cada opción y `PayerBadge.vue` al pagador en tabla y lista de gastos).
- **Liquidaciones**: tabla `settlements` (trip, from→to, amount_base) registra pagos entre viajeros ("Liquidar" en la vista Saldos; se pueden deshacer). Los saldos las descuentan de los netos y las sugerencias se recalculan. `Trip.debts_settled` (property, expuesta en TripRead → pill "Saldado" en tarjetas y cabecera) = hay liquidaciones y los netos quedan a cero; corta en `settlements` vacío para no cargar gastos en el listado. Al añadir ciudad/sitio al mapa mundial, `ensure_country_entry` arrastra su país (respetando hidden).
- **Categorías** de gastos y maleta viven en la tabla `categories` (kind expense|packing, POR FAMILIA), configurables desde /settings. Los defaults se siembran por familia (`services/categories.ensure_default_categories(db, family_id)` al crear familia/bootstrap; `ensure_default_categories_all` en arranque y restore, idempotentes). `Expense.category` es un string (no FK): renombrar una categoría propaga el cambio SOLO dentro de su familia (via `Trip.family_id`); borrarla deja el nombre huérfano. `GET /categories?trip_id=` devuelve las de la familia del viaje (invitados cross-familia).
- **Maleta**: una por viajero y viaje (`PackingItem.traveler_id`; NULL = maleta común). Matriz POR FAMILIA — en el viaje: la común es de todos; las maletas de TU familia se VEN todas y se editan salvo revocación expresa del dueño (ver /family arriba); las de otras familias NI SE VEN (`_bag_visible`/`_ensure_bag_editable`; `list_packing` y `selections` se filtran en el SERVIDOR con `_visible_items`, el selector pinta común (SIEMPRE primera y activa por defecto) → tuya → resto de familia; admin bypass total). `PackingTemplate`/`PackingTemplateItem` son POR VIAJERO (`traveler_id` dueño, unique nombre por dueño): toda tu familia las VE y puede aplicarlas (`_can_read_template`); las EDITA solo su dueño — o toda la familia si el dueño es un virtual (`_can_edit_template`; detalle solo-consulta con pill candado; el admin lo ve y edita TODO, también en la lista). Crear plantilla: dueño = tú o un virtual de tu familia (el admin, CUALQUIER viajero); REASIGNAR el dueño de una existente (PATCH `traveler_id`) es solo-admin — en la UI, el chip de dueño del detalle es un Select para el admin. La asociación maleta ↔ plantilla se desvincula con `DELETE /trips/{id}/packing/selection?traveler_id=` (maleta editable; los items quedan; ✕ en el badge de plantilla) (guardar la maleta de OTRO usuario como plantilla → 403; la común nace del creador); apply = plantilla LEGIBLE + maleta destino editable, COPIA los elementos (overrides libres) y persiste la selección en `packing_selections` (trip, traveler → template); sync-from-trip = plantilla EDITABLE + maleta editable, acepta `?traveler_id=` (el botón sync solo aparece si la plantilla seleccionada es tuya o de un virtual; selección que apunta a plantilla de otra familia → badge genérico). /packing agrupa por dueño (avatar, "Tus plantillas" primero, AUTOSELECCIONA la primera de la lista) con selector de dueño al crear.
- Navegación principal: Viajes (/), Mapa (/map), Maletas (/packing), Familia (/family, para todos), Ajustes (/settings: tema/idioma/categorías; copia de seguridad solo admin) + menú de usuario en la cabecera (avatar → /profile, /admin si eres admin, /settings, logout). En desktop las secciones viven en la cabecera (`AppNav`, con el guion viajero); bajo `sm` bajan a una barra FLOTANTE al pie (`AppBottomNav`: icono + label, pill verde que viaja hasta la activa) y la cabecera se queda con logo y avatar — la lista de secciones y el "activo optimista" salen de `composables/useNavItems.ts` (solo se monta una de las dos barras); `<main>` compensa con `pb-28` y los toasts inferiores suben en móvil. Rutas nuevas: /login (meta public+bare, sin AppNav) y /profile (nombre/color/avatar del viajero + cambio de contraseña). **/admin es el panel de administración (solo admin, `views/AdminView.vue`; /travelers redirige)**: viajeros agrupados por familia (`FamilyGroup` + `TravelerItem` en `components/travelers/`, con el @username visible — lo resuelve `FamilyGroup` del listado admin de usuarios o de la sesión propia), badges Cuenta/Tú, alta con `TravelerFormDialog` (nombre + swatch de color + familia — "Sin familia" por defecto: asignarla es explícito — + cuenta opcional si eres admin), y para el admin TODO inline — crear/renombrar/borrar familias y ORDENARLAS con drag & drop (`vuedraggable` con handle `.tt-drag-handle`), mover viajeros de familia y gestionar cuentas (crear cuenta para un virtual, reset de contraseña, toggle admin, eliminar cuenta) desde un Popover por viajero. **/family es la página de familia (para todos, `views/FamilyView.vue`)**: tus miembros (reutiliza `TravelerItem`: renombrar/color de virtuales y de ti mismo) y el PERMISO DE MALETAS por miembro — default permitido, el toggle REVOCA (`BagEditRevoke` owner→editor, `PUT /family/bag-permissions/{traveler_id}`, `GET` devuelve `revoked` y `restricted_by`; endpoints en `routers/families.py`, store `stores/bagPermissions.ts`); una maleta revocada se sigue VIENDO pero queda solo-consulta (pill candado en PackingTab, `_ensure_bag_editable` lo corta en el servidor; virtuales y común no revocan, admin bypass). Rutas SIEMPRE en inglés aunque la UI sea en español.
- **Mapa mundial INTERACTIVO** (choropleth clicable): la geometría vive en `frontend/public/geo/` — `countries-50m.v1.topo.json` (Natural Earth vía world-atlas, dominio público, 241 países, 231 KB gzip) y `adm1/{CC}.v1.topo.json` (regiones de 190 países, ~5 MB en total, de 3 KB a 418 KB cada uno). NUNCA en `src/`: los .json de src acaban como chunks en el precache del SW. Se sirven desde `public/` con regla `CacheFirst` propia (caché `geo`, que `session.logout()` NO debe borrar) y se cargan perezosamente; `scripts/build-geo.mjs` documenta origen, licencia y regeneración. Reglas de la geometría de regiones: se generan TODOS los países salvo los DEMASIADO FINOS (`ADM1_TOO_FINE`: GB 232 distritos, TR, SI, LV, MK, MT, UG, AZ) y los que se DISUELVEN (ES/FR/IT: sus admin-1 son provincias, se agrupan por `region_cod` en comunidad/région/regione); los de una sola unidad se descartan al generar, contando geometrías. Nada de `-simplify` por porcentaje (redondeaba las esquinas y las fronteras parecían dibujadas a mano): `interval=600` (≈1 px a zoom 6) + `precision=0.001` (~110 m), el mismo criterio de cuantizar-en-vez-de-simplificar que usa TREK. ⚠️ Natural Earth mete basura en `iso_3166_2` (tabuladores, rellenos `AU-X02~`): el script la limpia y descarta lo que no case con `^[A-Z]{2}-[A-Z0-9]{1,3}$`, porque ese id acaba en la DB como `region_code`. Decodificación propia en `utils/topojson.ts` (~60 líneas, sin `topojson-client`) que además DESENROLLA los anillos que cruzan el antimeridiano (Rusia, Fiyi, Antártida) y añade su copia desplazada 360°, o el trazo pintaría franjas de lado a lado. Los features se identifican por código ISO NUMÉRICO → `isoNumeric.ts`. `utils/worldGeo.ts` da `mainlandBbox` (anillo de mayor área: sin él, encuadrar Francia se va a la Polinesia), `pointInFeature` (rayo, con agujeros: el Vaticano no es Italia) y `normalizeLon`; `useCountryCenter` saca el centro del polígono en vez de llamar al geocoder. Capas: `WorldChoroplethLayer` (países) y `WorldRegionLayer` (una por país); el estilo NO va por props — vue-leaflet reconstruye la capa entera al cambiar `geojson` y recorre todos los features al cambiar `optionsStyle`, así que se guardan las capas por código y se hace `setStyle` solo en las que cambian. **Rótulos**: la cartografía va en DOS capas (`voyager_nolabels` + `voyager_only_labels` en un pane propio a z-index 450) con el relleno EN MEDIO, y los rellenos son deliberadamente flojos (0,14-0,36 países; 0,3 regiones marcadas) — si no, el verde se come los nombres. **Regiones**: desde zoom 5 (`REGION_ZOOM`) se pintan las de TODOS los países que asoman por la pantalla (`countriesIn`, cajas por trozo para que Francia no aparezca desde la Polinesia; el del centro va primero), se marcan directamente y el backend arrastra el país (`ensure_country_entry`); adivinar "qué país miras" fallaba en cuanto el centro caía en el mar. La bandera del país se esconde mientras se ven sus regiones (markerPane 600 tapa el overlayPane 400 y robaba el clic) y su hueco lo ocupan los **chips** de arriba a la derecha (`regionChips`): con la bandera fuera y el relleno tapado por las regiones, son el único acceso a la ficha del país — van SOLO los países MARCADOS, porque un chip de país sin marcar daría de alta el país entero de un toque y sin preguntar. Tocar un país o una región NO da de alta nada: abre `WorldMarkCard` (mismo hueco flotante que la ficha) con año, mes y nota antes de confirmar — y mientras está abierta el objetivo se queda resaltado vía `hoveredCode`, que en táctil no hay hover. Las altas de `useWorldMarking` devuelven si salieron bien y la tarjeta solo se cierra con `true`, para que un fallo de red no se lleve la fecha y la nota recién escritas; quitar una región pasa por el mismo confirm que los países (dejó de ser "tan barato como marcarla" el día que marcarla costó una tarjeta). Tocar un país ya marcado abre `WorldCountryCard` (ficha flotante sobre el mapa, no un popup de Leaflet) con año, contadores, editar y quitar. Las opciones de año/mes salen de `utils/worldDates.ts`, compartidas con el formulario completo. ⚠️ `map.fitBounds` recibe PUNTOS sueltos, nunca un `latLngBounds` de la app: con `useGlobalLeaflet: false` vue-leaflet trae su propia copia de Leaflet y el `instanceof` falla ("Bounds are not valid"). ⚠️ `v-model:center` emite un `LatLng`, no la tupla que declara el modelo: la vista se le pide al mapa.
- **Mapa mundial** (`WorldPlace`, /world-places): diario POR FAMILIA — países (marcador de bandera emoji), regiones (ISO 3166-2 en `region_code`, solo desde el mapa: el router exige que `ES-CT` empiece por su `country_code`), ciudades y sitios con nota libre. Se auto-rellena en cada GET (`services/worldmap.sync_world_places(db, family_id)`, idempotente) con los viajes de la familia O donde participa un viajero suyo: países de viajes TERMINADOS, sitios visitados y sitios enlazados a gastos (auto=True, origin=nombre del viaje; borrar una entrada auto la marca hidden para que no reviva). Sin familia → GET devuelve `[]`. El nombre de países auto es el código ISO; el front lo traduce.
- Geocoding con `accept-language=es,en` (español donde hay traducción, inglés romanizado como fallback: "Taipéi", no 臺北; "Hanamichi-dori", no 花道通り). Tiles de CARTO sin API key (voyager en claro, dark_all en oscuro) vía `useMapTiles`; el backend pina Python 3.12 con `.python-version` (uv) para sobrevivir a los upgrades de Python del sistema.
- `ItineraryItem.end_day` permite estancias de varios días (agenda muestra filas "sigue"; el calendario un evento all-day multi-día).
- **Noches sin alojamiento** (`utils/lodging.ts`, frontend puro): el índice NOCHE→reservas (`coveredNights`) es la pieza reutilizable — una noche se nombra por el día en que te ACUESTAS, así que un hotel cubre `[check-in .. check-out−1]` y el viaje tiene una noche menos que días (⚠️ `buildLodgingByDay` de `itinerary.ts` NO vale: incluye el día del check-out a propósito). De ahí salen `tripNights`, los huecos agrupados en tramos y los solapes (`lodgingCoverage`). Se pinta en `trip/LodgingGapsCard.vue` (pestaña Resumen, con los tramos como pills) y como pill ámbar `mdi-bed-empty` en la cabecera del día de la agenda — SOLO si el viaje tiene algún alojamiento apuntado (`hasLodgingBookings`), si no un viaje durmiendo en casa de alguien saldría entero en rojo.
- **Traslados entre paradas** (`utils/transfers.ts`, frontend puro): haversine × `DETOUR_FACTOR` (1,3) y velocidad por modo (`TRANSFER_MODE_KEYS`/`_ICONS` en `constants.ts`: walk 4,5 · bike 14 · transit 25 · car 45 km/h). Un tramo > 300 km de un día CON reserva de transporte se marca `covered` (heurística tosca a propósito: `origin`/`destination` de las reservas son texto libre y no casan con los sitios): no suma a los totales del día, se pinta en azul con `mdi-plane-train` y SIN duración (la sabe el billete), y `dayFeasibility` no lo juzga — sin eso, todo día de vuelo salía en rojo por partida triple. `dayFeasibility` marca el día por `overlap` (con horas no da tiempo), `tooLong` (SIN horas, traslados + 1 h por parada > 12 h) o `tooFar` (salto > 300 km que nadie cubre). La línea del traslado va DENTRO de `AgendaItemRow.vue` (el bucle `<draggable>` no puede cruzar un boundary de componente) y se calcula desde el espejo local `lists[day]`, NO de `store.byDay`, para recalcular mientras arrastras. Es una estimación en línea recta y el tooltip lo dice; el día que haya router propio (`TT_ROUTING_URL` contra OSRM) basta con devolver el mismo shape. El selector de modo es un `ClusterBtn` iconOnly que en móvil baja a su propia fila (con los cuatro modos en la misma no caben las etiquetas de Agenda/Calendario).
- **Reserva ↔ sitio ↔ gasto**: al crear/editar una reserva con coordenadas, `services/booking_place.ensure_booking_place` la enlaza (`Booking.place_id`) al sitio más cercano — POI ≤300 m, town ≤5 km, city ≤15 km (gana el de menor distancia/radio) — o crea uno nuevo (categoría `lodging` para hoteles); cambiar las coords re-enlaza. Una reserva con coste crea su gasto AUTOMÁTICAMENTE al crearla o al estrenar coste (`_auto_create_expense`, best-effort: sin tasa disponible se salta y queda el endpoint manual `create-expense`, que sigue siendo la vía de regeneración tras borrar el gasto y rechaza duplicados con 400). La reserva lleva pagador propio (`Booking.paid_by_id`/`paid_by_common`, excluyentes como en Expense, selector reutilizable `PayerSelect.vue`) que el gasto generado hereda. Reserva y gasto generado quedan sincronizados en ambos sentidos: editar la reserva espeja título/fecha/sitio/importe/moneda/pagador en el gasto (`_sync_linked_expense`, rescala repartos por importes), y editar el gasto devuelve importe/moneda/pagador/descripción→título a la reserva; mover el día del gasto desplaza entrada Y salida de la reserva conservando duración y horas (el gasto muestra el día de entrada/salida inicial). Borrar la reserva borra su gasto espejo y el sitio `lodging` autocreado si queda huérfano (ciudades/POIs enlazados por cercanía no se tocan). Los vuelos llevan `flight_number` además del código de reserva. En la agenda del itinerario TODAS las reservas con fecha salen automáticamente como secciones con cabecera: transportes (azul, `mdi-plane-train`, día de salida), resto de reservas (ámbar, actividades/coche/otros) y alojamiento (violeta, `mdi-bed`, check-in → noche antes del check-out, al pie del día); todas enlazan a la pestaña Reservas (`?booking=id` la resalta). En el calendario los hoteles son bandas all-day violetas.
- `/country-image?q=` proxya el banner de Wikivoyage (fallback Wikipedia) para heros/cards; el front cachea por código de país (`useCountryImage`).
- `backend/app/routers/` — REST bajo `/api/v1`. Recursos anidados para listar/crear (`/trips/{id}/expenses`), rutas planas para mutar (`/expenses/{id}`).
- Gastos multi-moneda: `exchange_rate` se snapshotea en cada gasto; `amount_base = amount * rate` se guarda calculado. Tasas: cache en DB (`exchange_rate_cache`) → frankfurter.app. Todo en `services/rates.py` (`get_rate`, `resolve_rate`, `to_base`).
- **Backup/restore** (`services/backup.py`, `/api/v1/backup/export|restore`, UI en Ajustes, SOLO admin): ZIP formato 2 con snapshot de la DB (API backup de sqlite3, seguro con WAL — NUNCA copiar el fichero a pelo) + manifest + uploads (whitelist `uploads/(\d+|avatars)/…`; los ZIP formato 1 restauran igual). Restore valida (traversal, zip-bomb, `quick_check`, revisión alembic conocida), aparta lo anterior en `data_dir/pre-restore/`, corre `alembic upgrade head` y recrea `app.state.engine` en caliente (`get_db` tolera el close de la sesión del engine viejo); `app.state.backup_lock` serializa. ## Convenciones

- Tests backend: TestClient + SQLite en memoria (`tests/conftest.py`); `TT_DATA_DIR` se fija a un tmp ANTES de importar la app (get_settings usa lru_cache). Tests frontend: Vitest sin DOM (`*.test.ts` junto al código, solo lógica pura).
- **Calendarios de los formularios** (`utils/tripCalendar.ts` + `DateRangePicker.vue` + `ui/TripDatePicker.vue`): al apuntar una reserva, actividad, gasto o checklist, los días DEL VIAJE se pintan como un área de fondo para situar la fecha dentro del total. `spanClasses` da la geometría (first/last + `open-top`/`open-bottom` cuando la casilla de la misma columna en la semana de arriba/abajo también entra) y la usan LAS DOS capas: la franja del viaje (en la celda `td`) y el relleno de la selección y del hover (en el día), así encajan una en otra y las semanas se funden en un área en vez de quedar en tiras. Las líneas van en `box-shadow` inset por lado (un `border` movería la rejilla) compuestas con variables, porque una regla por lado se pisaría. ⚠️ No se funde contra días de OTRO mes: no llevan marca y el área quedaría descosida. ⚠️ `isoKey` parsea la fecha ISO a mano: `new Date('2026-09-05')` es UTC y al oeste de Greenwich el viaje empezaría la víspera. El popover del rango se abre en el mes del VIAJE cuando aún no hay fecha elegida (si no, aterrizas en el mes actual y no ves el área).
- ⚠️ **PrimeIcons gana a Tailwind**: `.pi` fija `font-size: 1rem` y en el bundle acaba DESPUÉS de las utilidades, así que un `text-xs` sobre un icono NO hace nada (todos los `.pi` de la app miden 16 px). En `style.css` solo se rescata `.pi.text-4xs` (el chevron de las notas de gastos); arreglarlo para todos los tamaños encogería media app de golpe.
- Fechas naive (sin timezone) en toda la app: `toIsoDate()` en el front evita sorpresas de zona horaria con `DatePicker`.
- Dinero: `Decimal` en backend, importes serializados como float en las respuestas.
